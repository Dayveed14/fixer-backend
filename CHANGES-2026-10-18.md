# Fixer backend — changes (18 Oct 2026)

## Deploy checklist (in this order)

1. **Back up the database**, then run `migrations/2026-10-18_payments_zones_fixbot.sql`.
   If MySQL says "Duplicate key name" on one of the `ADD UNIQUE KEY` lines,
   that index already exists — skip that line.
2. Set environment variables on Render (see `.env.example`). In production
   the server now refuses to start if a required one is missing.
3. In the Paystack dashboard → Settings → API Keys & Webhooks, set the
   webhook URL to `https://<your-render-host>/api/payments/webhook`.
4. Set Render's health check path to `/api/health` (readiness with a DB
   check: `/api/health/ready`).
5. Deploy this backend and the matching frontend together — the payment
   flow changed on both sides.

## What changed

### Abuja dispatch pricing
- `config/pricing.js`: 29 Abuja areas grouped as city centre / inner
  districts / satellite towns. Fee = ₦1,000 + ₦150 per km of road
  distance to the Wuse workshop, rounded up to ₦500, minimum ₦1,500.
  e.g. Wuse ₦1,500 · Garki ₦2,000 · Gwarinpa ₦3,500 · Lugbe ₦4,000 ·
  Kubwa ₦4,500 · Gwagwalada ₦8,500. Edit a zone's `km` (or override its
  fee) in that one file.
- `GET /api/shipments/zones` (public) — the frontend's area picker.
- Shipments now store `user_id` and `pickup_zone`.

### Booking / pickup times
- `utils/schedule.js`: 8:00 AM – 10:00 PM Abuja time (server runs in UTC,
  so this is explicit). Calls are 30-min slots ending by 10 PM (last
  start 9:30 PM) with 1 hour's notice; pickups are 1-hour windows (last
  start 9:00 PM) with 2 hours' notice; up to 30 days ahead.
- `GET /api/bookings/slots?date=` and `GET /api/shipments/slots?date=`.

### Payments
- New flow: `POST /api/payments/initialize` → Paystack popup with the
  server's reference/amount → `POST /api/bookings` or `/api/shipments`.
- `services/paymentService.js`: server-side amounts; ownership,
  purpose and paid-for details checked; Paystack verification of
  status/amount/currency against the DB record; explicit states
  (pending/success/failed/abandoned/reversed/mismatch); booking/shipment
  created inside a transaction with the payment row locked; retries
  return the existing record; every change audited in `payment_events`.
- `POST /api/payments/webhook` (signature-verified, idempotent).
- Admin: `GET /api/payments?status=success&unfulfilled=true` lists people
  who paid but whose booking wasn't created; `GET /api/payments/:ref/events`.
- Paystack calls now time out (10 s) and outages leave payments pending.

### FixBot
- Identity only from a verified session (body `user_id` ignored).
- Rate limited: guests 8 / 15 min per IP, signed-in 20 / 15 min per account.
- Input limits (fault 200 chars, description 2,000, ≤20 symptoms), 100 KB body cap.
- AI fallback: per-caller (10/day) and global (300/day) budgets, 20 s
  timeout, output validated/normalised. Failures return a `no_match`
  answer (still HTTP 200) pointing to a technician instead of a 500.
- Outcome (`result_source`, `failure_reason`, `latency_ms`) recorded per
  request; one structured log line without customer text.

### Other hardening
- Registration: email format, password 8–72 chars, field lengths.
- Customer-supplied text is HTML-escaped in emails.
- Shipment status restricted to the agreed list.
- JSON 404 for unknown `/api` routes; 400 for malformed JSON; 413 for big bodies.
- `GET /api/health` and `/api/health/ready`; env validation at startup.

## Not changed / noticed
- There is no KYC feature in the backend yet, so there are no KYC tests.
- The admin Users/Technicians pages call `DELETE /api/users/:id`, which
  doesn't exist in the backend — delete buttons there will fail.
- AI budgets are in-memory: right for one Render instance; move to
  MySQL/Redis if you run several.

# Part 2 — repair lifecycle, notifications, pricing engine

## Deploy
1. Run `migrations/2026-10-18b_repair_lifecycle_pricing.sql` **after** the
   first migration. It adds the quote/approval/delivery columns, the
   `shipment_events` timeline (seeded for existing shipments), the
   pricing tables (seeded with today's prices), and widens payment
   purposes.
2. Deploy backend + frontend together.

## Shipment lifecycle
- Staff can only move a shipment to the **next** step
  (`PATCH /api/shipments/:id/status`, compare-and-set so two clicks
  can't skip a step).
- Diagnosis → **Waiting for approval** happens only through
  `POST /api/shipments/:id/quote { diagnosis, repair_cost }`. The return
  delivery fee for the customer's area is added automatically. The quote
  can be revised until the customer answers.
- Customer answers with `POST /api/shipments/:id/approval`:
  - approve → pays repair + return delivery (payment purpose `repair`)
  - decline → pays return delivery only (purpose `return`), unless that
    policy is switched off in Pricing.
  Same payment checks as before (server amount, owner, Paystack verify,
  one transaction, retry-safe).
- Repair can't start until approved and paid; a declined repair skips
  straight to Ready for delivery.
- Ready for delivery opens a confirmation window (default 12 h, set in
  Pricing). Customer taps "I've received my device"
  (`POST /api/shipments/:id/confirm-delivery`), or a background job marks
  it delivered automatically when the window ends (runs at startup and
  every 5 minutes).
- Every step is recorded in `shipment_events` and returned with the
  shipment for the timeline.

## Notifications and emails
- Every shipment step notifies the customer and admins in-app
  (`type`/`reference_type: "shipment"`); clicking opens that shipment.
- Customer emails: pickup scheduled, quote ready, ready for delivery — only.
- Admin emails: shipment initiated, repair approved/declined, delivery
  auto-confirmed — only.

## Pricing engine (admin → Pricing)
- `GET/PUT /api/pricing`, `/support-types`, `/zones`, `/settings` (admin only).
- Call prices, pickup areas (add, edit, switch off — never deleted),
  rate card (base, per km, rounding, minimum), delivery confirmation
  hours, and the decline-fee policy.
- Prices are read through `services/pricingService.js` (cached 60 s,
  cleared on save). If the tables are empty or missing, the launch
  defaults in `config/pricing.js` are used.

# Part 3 — technician jobs, call sessions, article visibility

## Deploy
Run `migrations/2026-10-18c_technician_jobs_meetings.sql` (after part 2).
Optional: Google Meet settings in `.env.example`.

## Articles and videos
- `GET /api/articles/:slug` and `GET /api/diy-videos/:slug` return
  **published only** again.
- New admin-only reads for any status: `GET /api/articles/manage/:slug`,
  `GET /api/diy-videos/manage/:idOrSlug` (this also fixes Edit Video,
  which was loading by id from a slug route).

## Repairs → technicians
- Starting a repair (`PATCH /api/shipments/:id/status` → `repair`) now
  requires `technician_id`; the technician is notified.
- `GET /api/shipments/assigned` — the technician's repairs.
- `POST /api/shipments/:id/repair-result { outcome: "repaired" | "unrepairable", note }`
  — no amount. The admin can move to quality check only after
  "repaired"; "unrepairable" goes back to the customer.
- Shipment status and quotes are now admin-only.

## Appointments
- MeshCentral sessions only for remote-support bookings (400 for voice/video).
- Video bookings get a meeting link when paid (Google Meet if configured,
  otherwise a Jitsi room); included in the booking email and response.
  `POST /api/bookings/:id/meeting` creates/replaces it.
- Bookings return `customer_phone` and `meeting_url`.
- Completing a booking also completes its ticket. Ticket completion
  never requires an amount (existing amounts are kept).

## Tests
The three tests that broke with your article/stats/env changes are
updated to the new behaviour; new suites cover the above.
